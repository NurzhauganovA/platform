# Fintend

Веб-платформа для наших проектов: закупы SKStore, предзаказы OMarket,
тендерный разбор и площадки, которые появятся дальше.

Платформа не переписывает проекты в себя. Каждый из них остаётся отдельным
пакетом со своим доменом, своей базой и своим CLI — платформа даёт им вход,
права, очередь задач и хранилище файлов. Локальный прогон двухгигабайтного
архива через терминал остаётся быстрее любого веба, и отказываться от него
незачем.

## Состояние

Подключены три проекта, и все три дают один и тот же рабочий список: что
покупают, почём это можем купить мы и сколько на этом заработаем. Площадки —
SKStore и OMarket — берут данные из кабинетов, тендерный отбор — из уже
разобранных папок с документацией.

```
GET  /api/health                 сводка по всем модулям
GET  /api/modules                из чего оболочка строит меню

GET  /api/skstore/worklist       закупы: себестоимость, маржа, что брать
GET  /api/skstore/item/{id}      разбор одной строки
POST /api/skstore/sync           забрать свежее с площадки
POST /api/skstore/analyze        пересчитать себестоимость (платно)
GET  /api/skstore/export         книга Excel

GET  /api/omarket/worklist       то же по предзаказам
POST /api/omarket/sync
POST /api/omarket/analyze
GET  /api/omarket/export

GET  /api/tender/worklist        отбор: за что браться и почём
GET  /api/tender/item/{id}       разбор одной закупки
GET  /api/tender/worklist/export книга отбора
POST /api/tender/upload-plan     что из выбранной папки нужно загружать
```

### Рабочий список

Главный экран всех трёх разделов. Плотная таблица, отсортированная так же, как
лист книги Excel того же проекта: сверху то, чем стоит заняться сегодня. У
площадок это «Фокус», у тендеров — «Отбор».

**Колонки в браузере и в книге совпадают буквально.** Не «примерно те же» —
таблица собирается из тех же `Column`, из которых пишется лист. Сотрудник
показывает коллеге экран, коллега открывает у себя файл, и они видят одно и
то же. Колонка, разошедшаяся на одну, — это полчаса выяснений, кто прав.

По умолчанию видно то, по чему принимают решение: товар, цена площадки,
себестоимость, маржа, срок. Кнопка «Все колонки» разворачивает лист целиком.

**Решение показывает цвет строки**, а не колонка на восемнадцать знаков: её
место отдано марже. Над таблицей стоит легенда — что означает каждый цвет и
сколько таких строк, — и она же служит отбором: щёлкнули «Участвовать»,
остались только они. У каждой строки рядом с цветом значок своей формы
(●&nbsp;◐&nbsp;○&nbsp;✕): при дальтонизме цвет сам по себе неразличим, а по
форме таблица читается и без него.

**Срок с отметкой.** «Сегодня» жёлтым — то, что горит, глаз находит сам, и
опять же словом, а не только цветом.

**Истёкшее в рабочий список не попадает.** Приём закончился — делать нечего,
а верх списка такие строки занимают: на живых данных их было 483 из 599.
Из базы они при этом **не удаляются**, и это осознанно: по ним видно, что мы
пропустили и почём уходило, на них держится история цен, а площадка ещё может
перевести их в «выиграли». Смотреть — «Все строки». Своё, где мы участвуем,
остаётся в списке и после срока: по нему ждут результата.

**Панель разбора тянется за левый край.** Ширины хватает на узкой таблице
конкурентов, но не на находках с объяснением «почему не тот товар»; на широком
мониторе панель в 672 точки читалась в три слова на строку. Ручка посередине
левой стенки, шаг — стрелками, двойной щелчок возвращает исходную. Ширина
запоминается: это личная настройка, как размер окна. Границы жёсткие с обеих
сторон — панель не сжать до полосы и не растянуть на весь экран: список, из
которого пришли, должен остаться виден.

**Длинные разделы свёрнуты, и видно, сколько в них.** «Предложения
конкурентов (7)», «Документы закупки (13)» — открываются щелчком. Что
сворачивать, решает сервер, а не длина: «как считали себестоимость» короче, но
важнее. Деньги и основания решения не сворачиваются никогда.

**Документы закупки — прямо в разборе.** Последний вопрос перед подачей всегда
«покажи само ТЗ», и до сих пор за ним выходили из платформы в папку на диске.
Теперь ТЗ, МЗ и КП открываются во вкладке: файл читается с места, а не из
копии — копия разошлась бы с папкой в день, когда заказчик пришлёт
исправленное ТЗ. Список файлов виден всегда, даже если архив не подключён:
знать, что в папке есть ТЗ, полезно и без возможности его открыть.

**Себестоимость можно пересчитать по своему поставщику.** Ядро берёт самую
дешёвую **из подходящих** находок — товар, который не проходит по
требованиям, поставить нельзя, какой бы ни была его цена, и непроходной
берётся только когда подходящих нет ни одной. Но «подходит» — суждение
модели: поставщик может быть незнакомым, срок неподъёмным, а с оценкой
тендерщик вправе не согласиться.

Поэтому в разборе видно, какая находка в расчёте, и любую другую можно
выбрать — деньги пересчитаются под неё. Считает при этом ядро, тем же кодом,
которым считается книга: свой расчёт в браузере разошёлся бы с ней на первой
же закупке. Каждая находка ведёт ссылкой на карточку товара — без неё она
обещание, а не поставщик.

**Разбор открывает сама строка** — щелчком или Enter с клавиатуры. Отдельной
колонки под кнопку нет: место в таблице дороже подсказки, о которой всё равно
догадываются с первого раза. Панель сбоку отвечает на
«откуда взялась цифра»: решение и почему, деньги с расчётом себестоимости
(«закуп 55 200 000 ₸ + доставка 2 500 000 ₸ + накладные 5%»), где взять со
ссылкой на находку, предложения конкурентов, что проверить перед подачей.
Порядок разделов тот же, что на листе разбора в книге. Закрывается по Esc.

**«Где купить» — значок, а не текст.** В книге это сорок четыре знака про
поставщика, срок и минимальную партию; в строке списка они растягивали её на
три линии и выталкивали маржу за край экрана. В списке от колонки нужен один
ответ — нашли или нет (`↗`) и не тот ли это товар (`⚠`), — а подробности
открываются разбором. Целиком текст остаётся в подсказке. Благодаря этому
весь рабочий набор колонок помещается на экран без прокрутки вбок.

**Фильтр в шапке колонки — как в Excel.** Значок воронки виден всегда, а не
по наведению: спрятанная возможность остаётся неизвестной. У текстовой
колонки — список значений с числом строк и поиском, у денежной и
процентной — «от» и «до» с настоящими границами данных в подсказках и
готовыми порогами («от 20%», «от 1 млн»), у даты — период.

Какие колонки фильтруются и чем, решается по данным, а не списком
заголовков. Числа и проценты получают диапазон, текст — список значений, но
только там, где значения повторяются: «Категория» повторяется, «Название
закупки» уникально в каждой строке, и список из трёхсот пунктов не фильтр, а
способ потерять время. Раздел, который добавят следующим, получит фильтры
сам.

Счётчики считаются по всему, кроме себя: выбрал категорию — напротив
заказчиков стоит, сколько их в этой категории. Строка без значения под
условие «маржа выше двадцати» не подходит: неизвестная маржа — не то же
самое, что подходящая.

**Итоги считаются по тому, что на экране.** Шесть плиток над таблицей —
показано строк, стоит взяться, объём закупок, заработаем, маржа посередине,
не с чем сравнить — пересчитываются после каждого фильтра. Плитка,
показывающая «265 закупок» после того, как оставили одну категорию, не
отвечает ни на один вопрос, а спрашивают у неё ровно одно: сколько денег в
том, что я сейчас вижу.

Набор плиток собирается из ролей колонок, которые объявил модуль: у площадок
в книге цена за единицу, складывать её по строкам нельзя — плитки «объём» там
не будет. Маржа берётся медианой, а не средним: одна закупка с маржой в
тысячу процентов — а такие в данных есть, это ненайденный товар — утаскивает
среднее туда, где не лежит ни одна строка.

**Отбор живёт в адресе.** `?tone=good&v.kategoriya=Электроника и ИТ&r.morzha_percent=20..`
— такую ссылку можно переслать коллеге, и он откроет ровно тот же список, а не
будет собирать условия заново с чужих слов. Активные фильтры показаны
снимаемыми метками над таблицей: строка «показано 26 из 292» без объяснения
читается как поломка.

**Чтение не тратит денег.** Страница показывает уже посчитанное; поиск на
внешних рынках идёт отдельной задачей по кнопке «Пересчитать». Иначе F5
списывал бы со счёта, а нажимают его часто.

**Тендерный отбор — тот же экран, но без кнопок прогона.** Закупки приходят
папками с документами, и разбор идёт у тендерщика на машине, где эти папки
лежат: платформа читает то, что он уже разобрал, — паспорта документов,
решения модели, находки на рынках, — и собирает из этого те же 265 строк, что
в его книге. Своей сборки книги здесь нет: и экран, и выгрузка идут через
`row_values` и `write_ranked` ядра. Список пересобирается один раз на
состояние базы (девять секунд на сто двадцать три корня) и потом отдаётся из
памяти; кэш сбрасывается не по сроку, а по содержимому — прогнали разбор у
себя, и платформа это увидит.

### Аналитика

Второй экран каждого раздела: тот же список, свёрнутый в разрез. Строк,
сколько стоит взяться, объём, себестоимость, заработок, медианная маржа и
сколько строк вообще оценено — по каждой категории, заказчику или признаку
закупки.

**Главный разрез — категория**, потому что вопрос «в чём мы сильны» задают
чаще прочих: отдел силён не во всём, и пока триста строк лежат одним списком,
это знание не работает. Разрез переключается на заказчика, папку, признак
закупки — и живёт в ссылке, как и отбор.

Состав колонок подстраивается под раздел сам, по ролям. У площадок в книге
цена за единицу — складывать её по строкам нельзя, и графы «объём» там нет.
Закупщик не увидит ни заработка, ни себестоимости: сервер вырезал эти колонки
по правам, и считать по ним нечего.

Маржа берётся медианой, а не средним. В живых данных попадаются закупки с
маржой в шестьдесят тысяч процентов — это найденный не тот товар, и одна
такая строка утаскивает среднее туда, где не лежит ни одна.

Считается из того же ответа, что рисует таблицу, и берётся из общего кэша
запросов: переход между списком и аналитикой мгновенный, второго мегабайта
по сети не идёт.

### Кто что видит

Себестоимость, маржа и наша цена — только тендерщику. Закупщик видит, где
взять товар и почём его отдаёт поставщик: это его работа. Наблюдатель — то,
что и так открыто любому участнику закупа.

Граница проходит в ответе API, а не в браузере: спрятать колонку на экране и
отдать её в JSON — самый распространённый способ отдать себестоимость наружу.
Колонка, которую не внесли в `modules/<slug>/columns.py`, считается денежной и
достаётся только тендерщику — отказ по умолчанию.

### План загрузки

Самый содержательный из них — последний. Браузер выбирает папку, считает
sha256 каждого файла **не загружая их**, и спрашивает платформу, что делать.
В ответ приходит план: неподдерживаемые форматы отсеяны, файлы с уже
разобранным содержимым не передаются вовсе.

На реальной папке закупки из двенадцати файлов грузится один:

```
всего:            12
грузить:          1  (12 КБ)
уже разобрано:    9
не читается:      2
```

Это не оптимизация ради оптимизации. Кэш разбора ключуется по содержимому, и
за девять из этих файлов уже заплачено — ни передавать их, ни разбирать заново
не нужно.

## Устройство

```
platform/
├── apps/
│   ├── api/          FastAPI: каркас и модули проектов
│   │   └── src/platform_api/modules/
│   │       ├── table.py    колонки книги → таблица в браузере, права
│   │       ├── skstore/    закупы Самрук-Қазына
│   │       ├── omarket/    предзаказы OMarket.kz
│   │       └── tender/     разбор тендерной документации
│   └── web/          React: оболочка, рабочие списки, загрузка папок
├── infra/            развёртывание и подготовка контекста сборки
└── docker-compose.yml   PostgreSQL и Redis для разработки
```

Проекты подключаются editable-зависимостями из соседних каталогов и физически
внутрь монорепо не переносятся.

### Базы

Один PostgreSQL, четыре базы: `fintend` у платформы и по одной у каждого
ядра. Врозь их держать не за чем, вместе — нельзя: у каждого проекта свои
миграции, и общая схема означала бы, что правка в одном ломает соседа.

SQLite, на котором skstore и omarket жили изначально, остался только для
запуска проекта в одиночку на своей машине. Для платформы он не годится:
к базе одновременно ходят почасовые прогоны и открытые страницы, а пишущий
в файл блокирует его целиком — читатель получает «database is locked» ровно
в тот час, когда работают все. Платформа считает файловую базу неисправностью
и говорит об этом в сводке готовности.

Переезд делается командой самого проекта, а не руками:

```bash
skstore db-copy --to postgresql+psycopg://...   # схему до этого ставит alembic
```

Она переносит таблицы порциями, помечает наивное время из SQLite как UTC —
иначе PostgreSQL прочитал бы его по поясу сервера и сроки уехали бы на пять
часов, — переставляет счётчики автономеров и сверяет число строк с обеих
сторон. Непустая целевая таблица для неё ошибка: повторный запуск иначе
удваивает данные, а обнаруживается это по числам в отчёте неделей позже.

### Контракт модуля

Проект сообщает о себе одним объявлением, и каркас сам его подхватывает:

```python
module = ModuleSpec(
    slug="tender",
    title="Тендеры",
    router=router,  # свои эндпоинты
    nav=(NavItem("Отбор закупок", "/tender/worklist"),),
    jobs=(analyze, sourcing),  # свои фоновые задачи
    health=health.check,  # своя проверка готовности
)
```

Добавление нового проекта не должно требовать правок в каркасе. Как только для
этого понадобится «ещё одно место, где перечислены модули», контракт перестал
работать.

Внутри модуля не должно быть предметной логики — только перевод на язык HTTP.
Если сюда переедет расчёт цены или разбор документа, одно и то же начнёт
считаться двумя способами, в вебе и в CLI, и они разойдутся ровно на той
закупке, где ошибка стоит дороже всего.

## Интерфейс

Оболочка строит меню из `/api/modules` — из того, что модули сами о себе
объявили. Подключение нового проекта не требует правок во фронтенде.

Ключевой экран — рабочий список. Он одинаков во всех трёх разделах: таблица,
собранная из колонок книги Excel того же проекта, цветная легенда над ней и
разбор строки сбоку. Сотрудник половину дня проводит в книге, и переучиваться
на другой способ читать те же данные ему незачем.

Что показывать, решает сервер. Колонки, слова легенды и набор кнопок приходят
в ответе `/worklist`: слова у разделов разные — площадка говорит
«участвовать», тендерный отбор «брать», — а кнопка, которую нечем обслужить,
хуже отсутствующей. В тендерном отборе кнопок обновления и пересчёта нет
вовсе: закупки приходят папками с документами, и разбор идёт у тендерщика на
машине, где эти папки лежат. Платформа показывает то, что он уже разобрал,
вместе с решениями модели и находками на рынках.

Загрузка папки закупки в интерфейсе сейчас скрыта, но жива: страницы
(`features/tender/CasesPage`) и эндпоинты (`/api/tender/cases`) на месте.
Человек выбирает папку, ту же, что лежит у него на диске; браузер считает
sha256 каждого файла, **не отправляя их**; платформа отвечает, что из этого
нужно грузить. До загрузки видно четыре числа: всего файлов, сколько передать,
сколько уже загружено, за сколько не придётся платить. На папке закупки это
секунды, на архиве в два гигабайта — часы разницы.

Оформление — не подбор на глаз: палитра проверена на различимость при
дальтонизме и на контраст с поверхностью, в светлой и тёмной темах. Цвет
состояния никогда не идёт без подписи.

## Запуск в контейнерах

Всё, что нужно, — Docker и заполненный `.env`.

```bash
cp .env.example .env      # впишите GEMINI_API_KEY
make up                   # интерфейс на :8080, API на :8000
make user                 # завести сотрудника
```

`make up` соберёт образы, поднимет базу, очередь, API, исполнителя и nginx,
накатит миграции и покажет адреса. Дальше:

```bash
make logs     поток журналов API и исполнителя
make ps       что запущено
make check    готовность модулей: что настроено, чего не хватает
make down     остановить
```

### На сервере

`make prod` вместо `make up`: 80 порт, домен `bcorp.kz`, журнал строками JSON,
перезапуск после перезагрузки машины. Порты базы, очереди и API привязаны к
самой машине — из сети к ним ходить незачем, а открытый 5432 это доступ к
себестоимости в обход платформы и её ролей.

Предел на тело запроса — 100 МБ: тендерная папка приходит целиком, сканы МЗ и
ТЗ бывают по десять мегабайт штука. На один файл платформа пускает
шестьдесят четыре, и всё, что между, отвергает уже она — словами и с
указанием предела.

**Платформа отвечает по HTTP.** Пароль и кука сессии идут открытым текстом;
в офисной сети это терпимо, наружу — нет. Место под сертификат в конфигурации
уже есть, включение не требует правки файлов. Порядок — в `infra/README.md`.

Перенос данных и копии — тремя скриптами:

```bash
./infra/backup.sh                        # четыре базы и загруженные файлы
./infra/restore.sh backups/<дата>        # он же разворачивает переезд
./infra/repath.sh /srv/fintend/тендеры   # пути документов под новый архив
```

Копия проверяется на читаемость сразу при снятии: битый дамп выглядит как
обычный файл, и узнают об этом в тот единственный день, когда он нужен.
`repath.sh` переписывает абсолютные пути документов в базе ядра — без него
список файлов в разборе виден, а открыть их нельзя.

### Что подключается с машины, а что живёт в образе

В образ уезжает только код. Данные и секреты подключаются томами, и это не
осторожность ради осторожности:

| Подключается | Почему не в образе |
| --- | --- |
| `.env` платформы и трёх проектов | ключи к моделям и доступ к площадкам; образ уезжает в реестр целиком |
| `data/` каждого проекта | база skstore весит 400 МБ, и внутри образа она устарела бы в тот же день |
| `exports/` | книги Excel должны оказаться на машине, а не в контейнере |
| `companies.toml`, ключ сервисного аккаунта | реквизиты и секрет, правятся без пересборки |
| хранилище загруженных папок | том, переживает пересборку |

Поэтому контейнер работает ровно с теми же данными, что и терминал: выгрузили
через кнопку — видно в CLI, и наоборот.

Одно исключение — адрес базы тендерного ядра. В его `.env` стоит `localhost`,
и это правильно: тендерщик гоняет разбор у себя, где база рядом. Внутри сети
Compose `localhost` — это сам контейнер, поэтому `docker-compose.yml`
переопределяет `TENDER__DB__URL` на службу `postgres`. Файл на машине при этом
не трогается. У skstore и omarket базы файловые, и им хватает `data/`.

Каталоги проектов ищутся рядом. Если раскладка другая:

```bash
make up OMARKET_DIR=~/code/omarket
```

### Чего контейнер не делает

**Вход в кабинет OMarket по ЭЦП.** Площадка требует подписи ключом в окне
настоящего браузера, а ключ лежит у сотрудника — там ему и место. Вход
делается на машине (`omarket login`), контейнер работает с оставшейся
сессией: её файл подключён вместе с `data/`. Сама выгрузка предзаказов идёт
уже в контейнере — Chromium для неё стоит в образе исполнителя.

## Запуск с машины

Так быстрее правится код: перезагрузка занимает секунду, а не пересборку.

macOS: системный `python3` — 3.9, поэтому окружение создаётся Homebrew-питоном.
Системный `node` — 18 и сломан обновлением icu4c, поэтому фронтенд работает
через `node@22`.

```bash
/opt/homebrew/bin/python3.12 -m venv .venv
.venv/bin/pip install -e "apps/api[dev]" python-dotenv
.venv/bin/pip install -e ../tender-analyze -e ../skstore -e ../../github/omarket

cp .env.example .env          # ключи моделей и параметры
docker compose up -d          # только PostgreSQL и Redis
cd apps/api && ../../.venv/bin/alembic upgrade head && cd ../..

.venv/bin/python -m platform_api               # API на :8000
.venv/bin/python -m platform_api.jobs.worker   # исполнитель очереди

export PATH="/opt/homebrew/opt/node@22/bin:$PATH"
cd apps/web && npm install && npm run dev      # интерфейс на :5173
```

`docker compose up -d` поднимает только инфраструктуру: приложение живёт под
профилем `full`, и рабочий режим разработки не меняется.

Первая учётная запись: `platform-admin create-user --email … --org fintend`.
Документация API — `http://127.0.0.1:8000/api/docs`.

## Разработка

```bash
.venv/bin/ruff format . && .venv/bin/ruff check --fix .
cd apps/api && ../../.venv/bin/mypy src && ../../.venv/bin/pytest

cd apps/web && npx tsc -p tsconfig.app.json --noEmit && npx playwright test

# Против собранного интерфейса, а не сервера разработки:
E2E_BASE_URL=http://localhost:8080 npx playwright test
```

Сквозные проверки идут против настоящего API и настоящей базы: то, что ломается
на стыке — кука сессии, поток прогресса, прокси, — в тестах отдельных слоёв не
видно. Серверы они не поднимают сами, чтобы не трогать рабочие данные без
ведома человека.

Тесты платформы не трогают настоящее ядро: у него своя база, свои реквизиты и
свой ключ к модели. Проверяется перевод на HTTP, а не разбор документов — за
это отвечают тесты самого ядра.
