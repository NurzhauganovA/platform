# Карточка лота: что это и каким должен стать редизайн

Задание для дизайнера-разработчика. Нужен новый экран карточки лота на React —
современный, красивый, удобный. Ниже: что за бизнес, что за сущность, что уже
есть в данных и что именно надо переделать.

Читать целиком. Половина требований здесь — не про пиксели, а про то, почему
экран устроен так, а не иначе. Красивый экран, который врёт про деньги, хуже
некрасивого.

---

## 1. О компании и продукте

ТОО «Fintend» — казахстанская компания, участвующая в государственных и
коммерческих закупках. Покупает товар (компьютеры, серверы, оргтехника,
насосы, оборудование) и поставляет заказчикам, выигрывая тендеры.

`fintend-platform` — внутренняя CRM. В ней работает около 30 человек из пяти
отделов. Платформа собирает закупки с четырёх площадок и ведёт их сквозным
процессом от появления объявления до оплаты по договору.

Интерфейс полностью на русском. Адреса страниц — латиницей.

### Откуда берутся лоты

| Площадка | Что это | Объём |
|---|---|---|
| **Госзакупки** (`goszakup`) | Портал `zakup.gov.kz`, обход по списку кодов ЕНС ТРУ | 184 лота, 21 действующий |
| **SKStore** (`skstore`) | Электронная площадка закупок | 1124 закупа |

подходящий и нажимает «Взять в работу» — так появляется **карточка лота**, о
которой этот документ.

## 2. Что такое карточка лота

**Одна карточка на лот и один статус на весь путь.** Отделов пять, у каждого
свой взгляд на закупку, но вопрос на планёрке один — «что сейчас с этой
закупкой». Сложение пяти состояний даёт пять разных ответов, поэтому статус
один.

**Снимок закупки хранится копией**, а не ссылкой в базу площадки. Выгрузка
пересобирает список каждый час, суммы у заказчика меняются, а карточка должна
остаться той, по которой её завели. Это важно для дизайна: на экране есть и
снимок (каким лот был), и живой разбор с площадки (какой он сейчас) — это
разные блоки, и путать их нельзя.

### Ключевые поля карточки

```ts
type Card = {
  id: string;
  code: string;            // «GZ000190» — постоянный код, им лот называют вслух
  module: string;          // "goszakup" | "skstore" | "omarket" | "tender"
  row_id: string;          // номер лота на площадке, «17546741-1»
  source_number: string;   // номер закупки (у объявления с 4 лотами он общий)

  title: string;           // название. ВНИМАНИЕ: у госзакупок сюда попадает
                           // техническая спецификация целиком — до 3000 знаков
  customer: string;        // заказчик
  amount: number | null;   // плановая сумма заказчика, ₸
  enstru_code: string;     // код ЕНС ТРУ, «262013.000.000011»
  category: string;        // наша категория товара

  status: LotStatus;       // одно из 14 состояний, см. ниже
  status_name: string;     // то же словом
  step: number;            // какой это шаг пути (1..11); 0 — сошёл с дистанции
  participation: "maybe" | "yes" | "no";
  skip_reason: string;     // почему не участвуем

  manager: string;         // кто ведёт лот как менеджер
  manager_id: string;
  owner: string;           // кто сейчас за него отвечает
  owner_id: string;

  deadline: string;        // окончание приёма заявок, ISO
  left: string;            // «5 ч. 20 мин.» — уже посчитано сервером
  burning: boolean;        // горит: осталось мало
  overdue: boolean;        // срок прошёл

  approve_by: string;      // до какого момента собрать подписи
  approve_left: string;
  approve_burning: boolean;
  approve_overdue: boolean;

  note: string;
  won_amount: number | null;  // за сколько выиграли
  winner: string;             // кто выиграл, если не мы
  submitted_at: string;
  finished_at: string;

  approvals: Sign[];       // пять подписей, см. ниже
  approved: boolean;       // все ли собраны
  open_tasks: number;
  done_tasks: number;
  can: string[];           // что доступно ЭТОМУ человеку прямо сейчас
};
```

### `can` — главное правило интерфейса

**Что можно нажать, решает сервер.** В поле `can` приходит список: доступные
целевые статусы плюс `decide`, `assign`, `sign`, `task`.

Второй набор правил в браузере однажды разъедется с серверным, и человек
нажмёт кнопку, получив отказ, — уже будучи уверенным, что сделал. Кнопка,
которую нечем обслужить, хуже отсутствующей.

**В дизайне:** никогда не рисовать действие, которого нет в `can`. Не «серым и
задизейбленным», а не рисовать вовсе — либо, если это важно объяснить,
показывать с человеческой причиной («нужны все пять подписей»).

## 3. Четырнадцать состояний лота

Основной путь (11 шагов):

| Ключ | Название | Смысл |
|---|---|---|
| `new` | Новый | Взяли в работу, ещё не смотрели |
| `discussion` | Обсуждение | Пишем замечание к техспецификации заказчику |
| `analysis` | На разборе | Считаем себестоимость, ищем товар, решаем участвовать ли |
| `approval` | На согласовании | Собираем пять подписей |
| `ready` | Готов к участию | Подписи собраны, можно подавать заявку |
| `awaiting` | Ожидаем итоги | Заявка подана, ждём результат |
| `won` | Выиграли | Победили |
| `contract` | Договор | Подписываем договор |
| `fulfilling` | Исполнение | Везём и поставляем товар |
| `awaiting_payment` | Ожидаем оплату | Поставили, ждём деньги |
| `done` | Завершён | Деньги получены |

Сошли с дистанции (3 состояния, вне основного пути):

| Ключ | Название | Смысл |
|---|---|---|
| `skipped` | Не участвуем | Решили пропустить |
| `lost` | Проиграли | Выиграл другой |
| `cancelled` | Отменён | Заказчик отменил закупку |

### ⚠️ Изменение: переходы свободные

Сейчас переходы описаны таблицей — из «Нового» можно только в «Обсуждение» или
«На разбор», обратно нельзя, из «Отправлено» вообще никуда.

**Заказчик требует убрать эти ограничения.** Компания — стартап, процесс ещё
не устоялся, и человек должен уметь перевести лот **из любого состояния в
любое**: из «Нового» сразу в «Завершён», из «Завершён» обратно в «Новый».

**В дизайне это значит:** блок смены статуса перестаёт быть коротким списком
«что дальше» и становится полноценным выбором из четырнадцати. Нужен способ
показать все четырнадцать так, чтобы это не превратилось в свалку: сгруппируй
по смыслу (подготовка → участие → исполнение → сошли), покажи текущее, дай
понять, какой шаг «естественно следующий», но не запрещай остальные.

Два ограничения всё же остаются, и они про деньги, а не про порядок:

- **«Готов к участию» требует всех пяти подписей.** Лот, объявленный готовым
  без подписи снабжения, — это участие в закупке, товара под которую нет.
- **«Не участвуем» требует причины.** Через месяц спросят, почему пропустили
  закупку на 40 миллионов, и «просто так» не подойдёт.

Эти два оставь как есть, но покажи их не отказом после нажатия, а понятным
состоянием до него.

## 4. Люди: роли и отделы

**Роль — про право видеть цифры. Отдел — про то, чья очередь работать.** Это
разные вещи, и в интерфейсе их путать нельзя.

### Десять ролей

| Роль | Кто это | Видит деньги |
|---|---|---|
| `admin` | Администратор | да |
| `analyst` | Тендерщик: разбор, себестоимость, маржа | да |
| `manager` | Менеджер поставки: ведёт лот через отделы | да |
| `head` | Руководитель | да |
| `commercial` | Коммерческий директор | да |
| `buyer` | Снабжение: ищет товар, подтверждает цены и сроки | **нет** |
| `technologist` | Технолог: проверяет техническую выполнимость | **нет** |
| `assembler` | Сборщик: собирает и настраивает оборудование | **нет** |
| `lawyer` | Юрист: замечания, договоры, суды | **нет** |
| `viewer` | Наблюдатель | нет |

**Жёсткое правило: снабжение, технологи, сборщики и юристы никогда не видят
себестоимость, маржу и заработок.** Это не настройка и не пожелание — сервер
таким ролям эти поля просто не присылает. В макете не рисуй их в местах, куда
заходят эти роли.

### Шесть отделов

`Обсуждение`, `Разбор`, `Снабжение`, `Юристы`, `Согласование`, `Подача`.

Задача адресуется отделу, а не человеку: уволившийся уносит очередь с собой.
Человек может взять задачу отдела себе.

## 5. Что сейчас на карточке и что с этим не так

Экран сейчас: двухколоночная сетка, слева содержимое, справа узкая колонка
действий. Работает, но выглядит как таблица из 2010-х и половину нужного не
показывает.

Блоки по порядку:

### 5.1. Шапка

`GZ000190 · <название>`, под ним заказчик, справа ссылка «Ко всем лотам».

**Проблема:** у госзакупок в названии лежит техническая спецификация целиком —
заголовок уезжает на три экрана. Сейчас обрезан в две строки.

### 5.2. Полоса хода (`Flow`)

Одиннадцать шагов полоской, текущий отмечен.

**Что нужно:** оставить идею, сделать красиво. Человек должен видеть, где лот
стоит и сколько до конца, а не одно слово без контекста.

### 5.3. Сведения (`Facts`)

Сетка из шести-восьми пар «подпись — значение»: осталось, сумма, площадка, лот,
ЕНС ТРУ, категория, выиграли за, победитель.

**Это снимок на момент взятия в работу.** Не путать с разбором (5.4).

### 5.4. Разбор закупки с площадки — **уже добавлен, нужно оформить**

Живые данные с площадки: объявление, что покупают, техническая спецификация,
соседние лоты объявления, документы закупки. Приходит секциями:

```ts
type DetailSection = {
  title: string;                 // «Объявление», «Что покупают», «Техническая спецификация»
  fields: DetailField[];         // пары подпись-значение
  table: DetailTable | null;     // таблица (соседние лоты, находки на рынке)
  note: string;                  // оговорка к разделу
  empty: string;                 // что сказать, если раздел пуст
  collapsed: boolean;            // показывать свёрнутым — решает сервер
};

type DetailField = {
  label: string;
  text: string;
  number: number | null;
  format: "text" | "money" | "percent" | "quantity" | "datetime";
  link: string | null;           // ссылка; вид «…/file/<sha256>» = документ закупки
  tone: "" | "good" | "warning" | "critical";
  note: string;                  // оговорка к значению
};
```

**Что нужно:** сделать этот блок читаемым. Сейчас это просто список секций.
Технические спецификации бывают на 3000 знаков — нужен способ читать их, не
прокручивая всю страницу. Документы должны открываться, не уводя с карточки.

### 5.5. Согласование (`Approvals`) — **переделать**

Пять подписей строками. У каждой: кто, когда, причина отказа.

```ts
type Sign = {
  kind: "manager" | "supply" | "legal" | "technologist" | "assembler";
  name: string;          // «Менеджер», «Снабжение», «Юрист», «Технолог», «Сборщик»
  state: "waiting" | "approved" | "rejected";
  by: string;            // кто подписал
  at: string;            // когда
  note: string;          // причина отказа
  can_sign: boolean;     // может ли ЭТОТ человек поставить ЭТУ подпись
};
```

Правила, которые надо сохранить:

- **Одна роль — одна подпись.** Если один человек может подписать за двоих,
  согласование перестаёт быть согласованием.
- **Готовым к участию лот не станет, пока не собраны все пять.**
- Подписи всегда в одном порядке: менеджер, снабжение, юрист, технолог,
  сборщик. Перестановка заставляет читать строку заново каждый раз.
- **Собирается за два часа до окончания приёма** (`approve_by`). Это запас не
  на подпись, а на подачу: заявку подают руками.
- Вопрос «кто это одобрил» возникает ровно тогда, когда закупка вышла в
  убыток — автор, время и причина отказа обязаны быть видны.

**Заказчик говорит: «пусть блок согласования не занимает много времени».**
Смысл: сейчас, чтобы подписать, надо найти свою строку среди пяти, понять, что
она твоя, нажать. Нужно, чтобы человек, зашедший подписать, увидел своё
действие мгновенно и сделал его в одно нажатие. Остальные четыре подписи —
контекст, а не работа.

Придумай форму: компактная полоса из пяти отметок с крупной кнопкой «Подписать»
для того, кому она адресована; отказ с обязательной причиной; наведение
показывает, кто и когда.

### 5.6. Задачи (`Tasks`) — **переделать**

```ts
type Job = {
  id: string;
  card_id: string; card_code: string; card_title: string;
  department: "discussion" | "analysis" | "supply" | "legal" | "approval" | "submission";
  department_name: string;
  title: string;
  body: string;
  assignee: string; assignee_id: string;   // пусто = задача отдела, ничья
  due_at: string; left: string;
  burning: boolean; overdue: boolean;
  state: "open" | "done" | "cancelled";
  result: string;         // ← сейчас есть в модели, но исполнитель его не пишет
  created_at: string;
};
```

Правила:

- **Задачи одной таблицей на все отделы.** «Мои задачи» у юриста, «запросы на
  поиск товара» у снабжения и «передать юристам» — одно и то же с разных
  сторон; пять таблиц означали бы пять раз чинить в них сортировку.
- **Задача всегда о лоте.** Очередь, где половина записей ни к чему не
  привязана, перестаёт быть очередью работы.
- Задача адресуется отделу; человек берёт её себе кнопкой.

**Что добавить: исполнитель пишет комментарий перед закрытием.** Сейчас задача
закрывается одной кнопкой, и что именно сделано — неизвестно. Поле `result` в
данных уже есть, его надо показать: при закрытии открывается короткая форма
«что сделано», текст сохраняется и виден в истории.

Сделай список задач компактным и по-другому: сейчас это просто перечень.

### 5.7. Файлы (`Files`)

Приложенные вручную документы: имя, размер, кто приложил, когда, заметка.
Загрузка перетаскиванием.

**Файлы лота — наши, а не заказчика.** Документы самой закупки лежат на портале
и приходят выгрузкой (они в блоке 5.4); здесь то, что приложили руками.
Отвязка от лота не удаляет из хранилища: тот же файл может быть приложен к
соседнему лоту.

### 5.8. Переписка (`Chat`) — **переделать в чат**

Внутренние реплики коллег по лоту. Не путать с «Обсуждением» (блок 5.9) — то
официальное обращение к заказчику, это разговор внутри компании.

```ts
type Message = {
  id: string;
  body: string;        // до 4000 знаков: это реплики, а не докладные
  author: string; author_id: string;
  created_at: string; edited_at: string;
};
```

**Что нужно:** сделать настоящим чатом, который открывается и закрывается по
нажатию. Сейчас это блок в общем потоке страницы, из-за чего он либо занимает
место впустую, либо теряется внизу. Нужен плавающий/выдвижной чат с счётчиком
непрочитанного.

### 5.9. Обсуждение — **добавить, сейчас на карточке этого нет**

Замечание к технической спецификации — официальное обращение к заказчику **до
подачи заявки**: мы указываем на требования, которые сужают круг участников до
одного поставщика, и просим их снять. Это ключевой инструмент бизнеса: снятое
требование превращает чужую закупку в нашу.

Текст пишет **ИИ (Gemini)**, человек правит и отправляет.

```ts
type Remark = {
  id: string;
  code: string; title: string; customer: string;
  amount: number | null; enstru_code: string; category: string;

  stage: "drafting" | "moderation" | "lawyers" | "sent" | "not_needed";
  stage_name: string;   // «Пишется», «На проверке», «У юристов», «Отправлено», «Не требуется»

  outcome: "waiting" | "accepted" | "rejected" | "closed" | "complaint";
  outcome_name: string; // «Ждём ответа», «Приняли», «Отклонили», «Закрыто», «Жалоба»

  writing: "queued" | "running" | "ready" | "failed";  // как идёт написание моделью
  trouble: string;      // что пошло не так у модели

  deadline: string; left: string; burning: boolean; overdue: boolean;

  assignee: string; assignee_id: string;
  text: string;         // текст замечания, который правят и отправляют
  ai_text: string;      // что написала модель — хранится отдельно
  ai_model: string;
  answer: string;       // ответ заказчика
  sent_at: string; answered_at: string;
  can: string[];        // этапы плюс `edit` и `resolve`
};
```

Правила:

- **Написанное моделью не переписывается правкой** (`ai_text` рядом с `text`).
  Сравнить отправленное с исходным нужно ровно тогда, когда пришёл отказ.
- **Отправка необратима.** Отправляют юристы и администратор: подпись под
  обращением от имени компании — не то право, которое даётся заодно с доступом
  к ценам.
- **Обсуждение не касается тендерного отбора** — только площадки. Туда закупки
  приходят папкой по почте, обсуждать их не с кем.
- Пока модель пишет, видно, что она пишет: `writing` = `running`.

**Что нужно на карточке:** блок, в котором видно состояние обсуждения, текст
(и что написал ИИ, и что правили), ответ заказчика, и можно писать/править
прямо здесь. Если обсуждения ещё нет — кнопка завести.

### 5.10. Кто работал над лотом — **добавить, этого нет вообще**

**Самое важное новое требование.**

Нужна лента всех, кто касался лота, от А до Я — как в Битриксе. Заказчик
объясняет прямо: «мы должны знать, кому премию выдать и узнать, кто работает
хорошо, по этим потом будем рейтинг считать».

То есть это не украшение, а основа для расчёта премий. Значит:

- Видно **каждое действие**: кто взял в работу, кто перевёл статус и куда, кто
  подписал и кто отказал, кто завёл задачу, кто её взял, кто закрыл и с каким
  комментарием, кто писал в чат, кто приложил файл, кто отправил замечание,
  кто записал итоги.
- У каждого события: **человек, роль, что сделал, когда**.
- Сводка сверху: сколько человек участвовало, кто сделал больше всего, сколько
  времени лот провёл на каждом этапе и у кого.
- Отдельно видно **автоматические действия** — часть событий делает не человек,
  а прогон по расписанию или ИИ. Записывать их автором нельзя: премию получит
  робот.

⚠️ **Важно для планирования:** таких данных в API сейчас нет. Есть только следы
по кускам — автор подписи, автор реплики, кто приложил файл. Сплошной ленты
событий по лоту нет, её надо добавлять на сервере. **Спроектируй блок так, как
он должен выглядеть, и опиши, какие поля тебе нужны от бэкенда** — мы их
сделаем.

Предлагаемая форма события (уточни, если нужно иначе):

```ts
type LotEvent = {
  id: string;
  at: string;                    // когда
  actor: string;                 // кто — имя
  actor_id: string;
  actor_role: string;            // роль на момент действия
  by_machine: boolean;           // сделано прогоном или ИИ, а не человеком
  kind: string;                  // "took" | "moved" | "signed" | "rejected" | ...
  title: string;                 // «Перевёл в «На разборе»»
  detail: string;                // подробность: причина, комментарий, куда
  from: string; to: string;      // для переходов
};
```

### 5.11. «Что дальше» (`Moves`) — **переделать**

Сейчас: список кнопок доступных переходов в правой колонке.

**Что нужно:** с учётом свободных переходов (раздел 3) это становится главным
органом управления карточкой. Сделай красиво и удобно: все четырнадцать
состояний, сгруппированные по смыслу, с подсветкой текущего и подсказкой, какой
шаг обычно следующий. Плюс отдельно: «Участвуем / Не участвуем» (`decide`),
назначение людей (`assign`), запись итогов подачи (`result`).

## 6. Что должно получиться

React-приложение (или набор компонентов) с полностью новым дизайном карточки
лота. Мы возьмём его как образец и перенесём в свой проект.

### Технически

- **React + TypeScript.** Стилевую систему выбирай сам, но учти: у нас
  **Tailwind 4**, и перенос будет проще, если и у тебя Tailwind.
- Данные — моки по типам выше. Покажи все интересные состояния: горящий лот,
  просроченный, отказ в подписи, обсуждение в работе у модели, лот, сошедший с
  дистанции, лот без разбора.
- Экран должен жить на ширинах от 1280 до 2560. Основные машины — ноутбуки и
  мониторы, мобильных нет.

### По содержанию — обязательно

1. Все блоки из раздела 5, включая три новых: **обсуждение**, **разбор**,
   **кто работал над лотом**.
2. **Свободные переходы** между всеми 14 состояниями.
3. **Комментарий исполнителя при закрытии задачи.**
4. **Чат, открывающийся и закрывающийся по нажатию.**
5. **Согласование в одно нажатие** для того, чья подпись нужна.

### Правила, которые нельзя нарушать

Это не стилистика — это вещи, на которых люди уже обжигались:

- **Цвет состояния всегда со значком или подписью.** Сам по себе он смысла не
  несёт: при дальтонизме «идёт» и «ошибка» неразличимы. Каждый цветной
  индикатор дублируется формой или словом.
- **Срок — самое заметное на экране.** Лоты горят часами. Если срок набран тем
  же серым, что остальное, горящий лот не отличается от спокойного.
- **Деньги не показываются тем, кому не положено.** Сделай варианты блоков для
  роли без доступа к деньгам — там, где были суммы, должно быть осмысленное
  содержимое, а не дырки.
- **Пустое состояние объясняет себя.** «Конкурентов ещё нет» и «карточку не
  читали» — разные ответы, молчание хуже обоих.
- **Ничего не мигает и не прыгает.** Список обновляется раз в минуту сам;
  подскакивающая при этом страница сбивает чтение.

### Чего не надо

- Не надо мобильной вёрстки.
- Не надо тёмной темы (можно, но это не приоритет).
- Не надо придумывать поля, которых нет в типах выше, — кроме блока «кто
  работал», где как раз нужно предложить состав данных.
- Не надо переносить сюда рабочие списки площадок и аналитику: это соседние
  экраны, здесь только карточка лота.
