# Развёртывание на сервере

Платформа отвечает на `bcorp.kz` по 80 порту. Ниже — что сделать на чистой
машине и в каком порядке.

## Как платформа доступна снаружи

Через **Cloudflare Tunnel**: `cloudflared` на самой машине принимает запросы
из Cloudflare и передаёт их в контейнер по петле.

| имя | куда ведёт |
|---|---|
| `bcorp.kz` | рабочая среда |
| `stage.bcorp.kz` | проверочная, `127.0.0.1:8081` |

Сертификатов на сервере нет и не нужно: TLS снимает Cloudflare, и до
контейнера доходит уже расшифрованный запрос. Портов в межсетевом экране тоже
открывать не надо — туннель ходит изнутри наружу, а не наоборот. Это заодно и
безопаснее любой схемы с открытым 443: у машины нет ни одного входящего
соединения из интернета.

Отсюда следуют две вещи, которые легко нарушить незаметно:

- **`PLATFORM__AUTH__SECURE_COOKIES=true`** в обеих средах. Браузер приходит по
  HTTPS, туннель шифрует весь путь, и куку с признаком `Secure` он отдаёт.
- **Настоящий протокол API узнаёт только из заголовка.** nginx видит обычный
  HTTP и передаёт дальше `X-Forwarded-Proto` от Cloudflare, а не свой
  `$scheme`. Подставь он свой — платформа считала бы, что человек работает по
  открытому протоколу.

Место под проверку владения доменом (`/.well-known/acme-challenge/`) в
конфигурации оставлено: пригодится, если туннель когда-нибудь заменят на
обычный вход по 443.

## Что нужно на сервере

- Ubuntu Server 24.04 LTS, диски в зеркале
- Docker Engine и плагин Compose из официального репозитория Docker
- `git`, `make`
- Постоянный адрес и запись `bcorp.kz` → адрес сервера в DNS
- Открыты 80 и 22, остальное закрыто

## Порядок

### 1. Репозитории

Собирается образ из четырёх деревьев: платформа плюс три подключённых
проекта. Они ставятся editable, поэтому нужны исходники, а не пакеты.

```bash
sudo mkdir -p /srv/fintend && sudo chown "$USER" /srv/fintend && cd /srv/fintend
git clone <platform> platform
git clone <tender-analyze> tender-analyze
git clone <skstore> skstore
git clone <omarket> omarket
```

Раскладка по умолчанию ждёт `tender-analyze` и `skstore` рядом с `platform`,
а `omarket` — на два уровня выше (так он лежит на машине разработчика). На
сервере всё рядом, поэтому путь к нему надо указать. Строкой в `.env`:

```
OMARKET_DIR=../omarket
```

Или в команде, если удобнее: `make prod OMARKET_DIR=../omarket`. Относительный
путь считается от каталога `platform`.

### 2. Настройки и ключи

```bash
cp .env.example .env
```

Заполнить: `GEMINI_API_KEY`, `PLATFORM__SECRET_KEY`, `TENDER_ARCHIVE`.

`TENDER_ARCHIVE` — путь к архиву тендерных папок **на этой машине**. Он
подключается в контейнер тем же путём: в базе ядра лежат абсолютные пути
документов, и другое место потребовало бы переписывать их на лету.

У подключённых проектов свои `.env` — они читаются из их каталогов. Базы там
задавать не нужно: адреса прописаны в `docker-compose.yml` и смотрят на
соседние базы того же PostgreSQL.

### 3. Проверка перед запуском

```bash
./infra/stage-projects.sh
```

Этим шагом начинается `make prod`: исходники трёх проектов переносятся в
контекст сборки. Если он падает — службы приложения не поднимаются вовсе, и в
`make ps` остаются только база и очередь. Скрипт называет проект, который не
нашёл, и переменную, которой поправить путь.

### 4. Первый запуск

```bash
make prod
```

Соберёт образы и поднимет всё: базу, очередь, API, исполнителя и nginx.

Схемы поднимаются сами — служба `migrate` заводит недостающие базы
(`fintend`, `fintend_tender`, `fintend_skstore`, `fintend_omarket`) и доводит
до головы схему платформы и трёх ядер. Идёт при каждом запуске и повторов не
боится.

После этого платформа открывается на `http://bcorp.kz`, но **разделы будут
пусты**: схемы есть, данных нет. Данные переносятся следующим шагом.

### 5. Данные

Без этого шага платформа работает, но показывать ей нечего: разбор тендеров и
выгрузки площадок лежат на прежней машине.

На прежней машине:

```bash
make backup                      # снимет четыре базы и загруженные файлы
scp -r backups/<дата> сервер:/srv/fintend/platform/backups/
rsync -a ~/Desktop/тендеры/ сервер:/srv/fintend/тендеры/
```

Часть имён на этом отвалится с `File name too long`. Предел ext4 — 255
**байт** на колено пути, macOS считает символами, а русская буква весит два;
такие имена на сервере не создать никак. Перенос от этого не прекращается:
rsync называет их, пропускает и довозит остальное, а в конце возвращает 23 —
это «доехало не всё», а не «не доехало ничего».

Сколько их, видно заранее:

```bash
find ~/Desktop/тендеры -print0 | python3 -c "
import os, sys
long = [p for p in sys.stdin.buffer.read().split(b'\0')
        if p and any(len(part) > 255 for part in p.split(b'/'))]
print(len(long), 'имён длиннее 255 байт')
for p in long[:5]: print(' ', os.fsdecode(p))
"
```

Единственное лечение — укоротить их на прежней машине **до** переноса и
прогнать по этим папкам разбор заново: в базе записаны старые имена, и
переименование на сервере разошлось бы с ней.

На сервере:

```bash
sudo chmod -R a+rX /srv/fintend/тендеры
./infra/restore.sh backups/<дата>
./infra/repath.sh /srv/fintend/тендеры
./infra/check-archive.sh
```

Права нужны первой строкой. Платформа работает не под тем, кто заходит по
ssh, а под своим пользователем (uid 10001) — так задумано: доступ к архиву
она получает ровно на чтение и ровно к нему. Архив же приезжает с правами
прежней машины, где домашние папки закрыты для всех, кроме владельца, и
платформа упирается в них на первом же файле. Выглядит это как «нет на
диске», хотя файл лежит на месте. Писать она туда не сможет и после `chmod`:
том подключён только на чтение.

`repath.sh` переписывает абсолютные пути документов в базе ядра под путь
архива на сервере. Без этого список файлов в разборе виден, а открыть их
нельзя: платформа ищет их там, где они лежали на машине тендерщика.

`check-archive.sh` сверяет то, что записано в базе, с тем, что видит сам API
изнутри контейнера, и говорит про каждый непойманный файл, почему он не
нашёлся: архив не подключён томом, путь ведёт на прежнюю машину, имя длиннее
предела или записано в другой форме Unicode. Снаружи все четыре выглядят
одинаково — «нет на диске», — и без разбора причины чинится не то.

Про форму записи имени платформа знает сама. Одну и ту же русскую букву
Unicode позволяет записать двумя способами, macOS ищет файл нечувствительно к
этому, ext4 сравнивает байты — и в базе одна и та же папка встречается в обоих
написаниях, потому что её переписывали разные прогоны. Поэтому файл ищется по
коленам, а диск не трогается: переименовать его под базу невозможно в
принципе — какую форму ни выбери, вторая половина путей перестанет сходиться.

Часть путей не выправит ничто: разбор распакованных архивов читал файлы во
временной папке, и в базе остался её путь. На выгрузке с рабочей машины это
пятнадцать процентов документов. Они вернутся, когда по этим папкам пройдёт
следующий разбор.

### 6. Сотрудники

```bash
make prod-user EMAIL=ivanov@bcorp.kz ROLE=analyst NAME="Иванов Иван"
```

Роли: `admin`, `analyst` (тендерщик — видит деньги), `buyer` (закупщик — видит,
где взять товар, но не себестоимость), `viewer`.

### 7. Копии

```bash
crontab -e
```

```
30 2 * * * cd /srv/fintend/platform && ./infra/backup.sh >> /var/log/fintend-backup.log 2>&1
```

Скрипт сам проверяет, что дампы читаются, и убирает копии старше двух недель.

**Копия рядом с сервером — не копия.** Пожар, залив и кража забирают машину
вместе с диском в ней. Раз в неделю копию надо увозить: внешний диск,
NAS в другом здании или облачное хранилище — что угодно, лишь бы не здесь.

Раз в квартал — проверочное восстановление на отдельную базу. Копия, которую
ни разу не разворачивали, — это надежда, а не копия.

## Проверочная среда

Второй набор служб на том же сервере. Проверять правки на рабочей — это
проверять на живых данных отдела: неудачная миграция или сломанный разбор
останавливают работу тридцати человек, а откат занимает больше, чем проверка.

Разведено всё: контейнеры (`fintend-stage-*`), сети, тома, базы и порты.
Рабочая среда при этом не трогается — команды разных наборов не видят чужих
контейнеров.

| | рабочая | проверочная |
|---|---|---|
| имя | `bcorp.kz` | `stage.bcorp.kz` |
| интерфейс | 0.0.0.0:80 | **127.0.0.1**:8081 |
| API | 127.0.0.1:8000 | 127.0.0.1:8001 |
| PostgreSQL | 127.0.0.1:5432 | 127.0.0.1:5433 |
| Redis | 127.0.0.1:6379 | 127.0.0.1:6380 |
| дерево | одно и то же — `/srv/fintend/platform` |

### Из одного дерева или из двух

Обычно хватает **одного дерева**: `make stage` и `make prod` из
`/srv/fintend/platform` поднимают разные наборы, и разведено между ними всё,
что считается данными.

| | разведено |
|---|---|
| контейнеры, сеть, тома | да, именем набора Compose |
| базы всех четырёх схем | да, свой PostgreSQL |
| образы (`platform_api` / `fintend-stage_api`) | да |
| загруженные файлы | да, свой том `storage` |
| порты | да |

Образы разные — это стоит запомнить: `make stage` пересобирает только свой, и
рабочая среда после перезагрузки машины поднимется на прежнем. Отсюда и
порядок работы: выкатили ветку в проверочную, посмотрели, и только потом
`make prod` пересобирает рабочую из того же дерева.

Не разведены три вещи, и все три — файлы на диске:

- **`data` подключённых проектов.** Главное здесь — сессия кабинета omarket
  (`data/session.json`): она одна, и два набора, ходящие в кабинет по ней,
  будут выбивать друг друга. В проверочной «Обновить данные» у omarket лучше
  не трогать.
- **`exports`.** Книги обеих сред складываются в один каталог. Не опасно, но
  выгруженный файл придётся опознавать по времени.
- **`.env`.** Один на обе, и это скорее удобно: ключи и `TENDER_ARCHIVE`
  совпадают. Адреса баз в нём не действуют — их задаёт `docker-compose.yml`,
  и внутри каждого набора имя `postgres` ведёт в свой.

Если этого мало — например, надо гонять omarket в обеих, — разворачивается
второе дерево, и тогда у проверочной свои каталоги проектов:

```bash
sudo mkdir -p /srv/fintend-stage && sudo chown "$USER" /srv/fintend-stage
cd /srv/fintend-stage
git clone <platform> platform && git clone <tender-analyze> tender-analyze
git clone <skstore> skstore && git clone <omarket> omarket
cp /srv/fintend/platform/.env platform/.env
for p in tender-analyze skstore omarket; do cp /srv/fintend/$p/.env $p/.env; done
cp /srv/fintend/tender-analyze/companies.toml tender-analyze/
```

В `.env` проектов адрес базы стоит через `localhost:5432` — это рабочая.
Внутри контейнеров он переопределён, но команда из терминала проверочного
дерева пошла бы в рабочую базу. Поправьте порт на 5433:

```bash
cd /srv/fintend-stage && sed -i 's/localhost:5432/localhost:5433/' */.env
```

Архив тендерных папок в обоих случаях общий: он подключается только на чтение.

### Обычный день

Из одного дерева, `/srv/fintend/platform`:

```bash
git pull                    # или git checkout <ветка>
make stage                  # соберёт свой образ и поднимет проверочную

make stage-logs             # что происходит
make stage-ps               # что запущено
make stage-user EMAIL=test@bcorp.kz ROLE=analyst NAME="Проверка"
```

Рабочая при этом продолжает работать на прежнем образе: `make stage` её не
трогает и не пересобирает.

Данные наливаются копией рабочих. Свежей, а не той, что осталась от переезда:
в старой пути к архиву ведут на машину тендерщика, и файлы не найдутся.

```bash
make backup                                                   # копия рабочей
STACK=fintend-stage ./infra/restore.sh backups/<дата>
STACK=fintend-stage ./infra/check-archive.sh
```

`STACK` обязателен во всех трёх скриптах `infra`. Без него они идут в
**рабочую** базу — и `restore.sh` разворачивает копию поверх неё, а
`repath.sh` переписывает её пути. Обе среды при этом отвечают одинаково, и
подмену человек не заметит.

Убедились, что работает, — тогда:

```bash
make prod
```

Пересобирает рабочую из того же дерева, которое вы только что проверили.

### Как её открыть

```
https://stage.bcorp.kz
```

Идёт через Cloudflare Tunnel: `cloudflared` на этой же машине принимает запрос
из Cloudflare и передаёт его на `127.0.0.1:8081`.

**Портов в межсетевом экране открывать не нужно, и открывать их нельзя.**
Проверочная привязана к петле (`WEB_BIND=127.0.0.1`), и это не перестраховка:
порт, открытый на всех адресах, был бы вторым входом в обход туннеля — без
его проверки входа и мимо журнала Cloudflare. А лежит в проверочной копия
рабочих данных вместе с себестоимостью и КП конкурентов.

Проверить с самого сервера:

```bash
curl -sI http://127.0.0.1:8081 | head -1
ss -ltnp | grep 8081        # должно быть 127.0.0.1:8081, не 0.0.0.0:8081
```

**Кука сессии — `true`.** В `.env` проверочного дерева:

```
PLATFORM__AUTH__SECURE_COOKIES=true
```

Браузер приходит по HTTPS, туннель шифрует весь путь до машины, и куку с
признаком `Secure` он отдаёт. Значение `false` здесь было бы не послаблением
ради удобства, а дырой: за этой кукой лежат себестоимость и маржа.

Работает это только потому, что nginx передаёт API настоящий протокол
заголовком `X-Forwarded-Proto`. Сам он видит обычный HTTP — TLS снимает
Cloudflare, до контейнера доходит уже расшифрованный запрос.

### Остановить

```bash
make stage-down
```

Тома остаются: следующий `make stage` поднимется с теми же данными. Удалить их
целиком — `make clean` из проверочного дерева.

## Что дальше

```bash
make logs                # поток журналов API и исполнителя
make ps                  # что запущено
docker compose -f docker-compose.yml -f docker-compose.prod.yml --profile full restart api
```

Обновление платформы: `git pull && make prod`. Образы пересобираются, тома с
данными остаются.

## Чего здесь пока нет

- **Расписание прогонов.** Почасовые разборы skstore и omarket пока
  запускаются кнопкой: планировщика в платформе нет.
- **Мониторинг.** Об упавшем исполнителе узнаёт тот, кто заметил, что задачи
  не идут.
